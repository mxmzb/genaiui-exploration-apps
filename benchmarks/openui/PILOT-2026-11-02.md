One sample per case establishes a working measurement path, not a framework or

[measurement revision](../MEASUREMENTS.md).

The twelve-card output included a known-subtotal metric even for records with a
known total. That was redundant but factually correct; it passed the requested
content oracle. Treat visual/editorial consistency as a separate review dimension.

An actual browser click on View Details for apartment 3 reached the app's public
agent handler with `{"action":"view_apartment","apartmentId":"3"}`. The benchmark
request sink saved the payload and returned an empty completion, with no further
paid call. This verifies dispatch, not the quality of a generated detail view.
Native-renderer unit tests additionally verify custom actions, required fields and
form-scoped submission. Full multi-turn journeys remain future measurement work.

## Additional application smoke checks

A separate standalone/headless-chat browser smoke produced a live three-apartment
comparison with real photos, then a generated form. An empty submit was blocked
locally. A valid submit sent exactly the actual apartment ID and synthetic form
values through the native action path to the provider. The final confirmation
screen was not retained when the development tab refreshed during the production
rebuild, so this is not a completed-journey benchmark pass.
